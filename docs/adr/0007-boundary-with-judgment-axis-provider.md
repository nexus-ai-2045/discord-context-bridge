# 決定記録 0007: 判断軸を持つ別の仕組みとは直接つながず、データの形の約束で結ぶ

## 状態

採用

## 背景

返信の相談（`reply_consultation.py`）は、判断軸と対人の決まりを持つ別の非公開の仕組み（現在は `LCS`）の資料を、そのリポジトリの中の配置ごと直接読んでいる。場所の指定（`--lcs-root` か `LCS_REPO_ROOT`）が無いと止まる。公開の `DCB` の一機能が、非公開の仕組みのファイルの配置を前提にしている。

あわせて、取得した記録をどこのデータベースに置くかが決まっていなかった。共有のデータベースを作ると、仕組みどうしが互いの形式に縛られる。各仕組みが原文の写しを持つと、二重保存になり、削除や同意の取り消しが漏れやすい。

## 決定

1. `DCB` は、判断軸を持つ別の仕組みを直接呼ばない。その仕組みのリポジトリの中の配置も前提にしない。
2. `DCB` が外へ渡すのは、版の番号つきの「文脈のまとまり」とする。中身は、取得の範囲、鮮度、根拠への参照。形式を変える時は版の番号を上げる。
3. 返信の組み立ては、`DCB` の文脈のまとまりと判断軸を組み合わせる上位の層（スキルなど）が行う。`DCB` も判断軸を持つ仕組みも、互いを知らずに単独で試験と公開ができるようにする。
4. 返信の相談の `--lcs-root` と `LCS_REPO_ROOT` は、「判断軸の参照先」という汎用の設定に改める。特定の仕組みの名前と配置に結び付けない。旧い名前の扱いは、実装の時に決める。
5. データの持ち主は、種類ごとに1つにする。
   - `Discord` の原文: `DCB` だけが持つ。置き場は決定記録 0006 のスレッドごとの台帳。
   - 検索用の索引: `DCB` が持つ。台帳から作り直せる読み物とし、必要になった時だけ `SQLite` にする。
   - 人物、プロフィール、本人が採用した判断、判断軸: 別の仕組みが持つ。原文は写さず、`DCB` の記録を指す参照（識別子と指紋）だけを持つ。
6. どのデータも利用者の手元の非公開の領域に置き、リポジトリには入れない。リポジトリが公開か非公開かは、コードの扱いだけを決める。

## 退けた案

- 今のまま `DCB` が別の仕組みの資料を直接読む案は、公開の道具が非公開の配置を知り続けるため棄却した。
- 共有のデータベースを1つ作り、全ての仕組みで読み書きする案は、互いの形式に縛られ、独立が崩れるため棄却した。
- 各仕組みが原文の写しを自前のデータベースに持つ案は、二重保存になり、削除と同意の取り消しが漏れやすいため棄却した。
- 返信の組み立てまで別の仕組みが行い、`DCB` は取り込みだけにする案は、公開の `DCB` の返信の支援が非公開側に閉じるため棄却した。

## 影響

良い影響:

- `DCB` は、判断軸を持つ仕組みが無くても試験と公開ができる。
- 原文が1か所にしか無いので、同意の境界と削除の扱いが単純になる。

トレードオフ:

- 文脈のまとまりの形式が公開の約束になり、変える時は版の番号を上げる運用が要る。
- 返信の相談の設定の名前を変える実装と、利用者の設定の移行が要る。
